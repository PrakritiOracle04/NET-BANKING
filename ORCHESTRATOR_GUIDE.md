# Banking Workflow Orchestrator Guide

The Banking Workflow Service is the orchestrator. Its job is to coordinate a money operation that touches multiple independent services, while keeping the final result consistent if one of them fails.

It does not replace Account, Beneficiary, or Transaction Service. Each still owns its own responsibility:

| Service | Owns |
| --- | --- |
| Account Service | Account state, balances, balance movements |
| Beneficiary Service | Who the customer is allowed to transfer to |
| Transaction Service | Transaction history and transaction status |
| Customer Service | Profile and KYC eligibility for account opening |
| Branch Service | IFSC validation |
| Bill Payment Service | Biller registrations and bill-payment state/history |
| Banking Workflow Service | The overall process, step order, idempotency, rollback, and recovery |

The public request path is:

```text
Client -> API Gateway :8080 -> Banking Workflow Service :8088
                                  -> Account Service :8085
                                  -> Beneficiary Service :8086
                                  -> Transaction Service :8087
                                  -> Bill Payment Service :8090
```

The important rule is: for money-moving operations, Workflow Service calls the participating services. Account Service does not call Beneficiary Service, and Beneficiary Service does not call Transaction Service.

The only intentional direct service-to-service call outside this pattern is the read-only mini-statement path:

```text
Client -> Gateway -> Account Service -> Transaction Service
```

That is fine because it is a read operation, not a multi-service money workflow.

## Routes handled by the orchestrator

All require:

```http
Authorization: Bearer <JWT>
Idempotency-Key: <unique-client-generated-value>
```

| Route | What Workflow coordinates |
| --- | --- |
| `POST /api/banking/deposit` | Account credit -> transaction record |
| `POST /api/banking/withdraw` | Account debit -> transaction record |
| `POST /api/banking/transfer` | Validate source -> validate destination -> validate beneficiary -> debit source -> credit destination -> record debit transaction -> record credit transaction |
| `POST /api/banking/accounts/open` | Validate profile/KYC -> validate branch -> idempotently create account |
| `POST /api/banking/bill-payments` | Validate account/biller -> create pending payment -> debit account -> record transaction -> complete payment |

The gateway merely forwards `/api/banking/**` to Workflow Service. It does not understand balance updates, rollbacks, or Saga state.

## Why the `Idempotency-Key` matters

Network failures are normal. A client may send a request, lose the response, and retry.

Without idempotency, this could happen:

```text
Client asks for Rs. 500 deposit
Workflow completes deposit
Response is lost
Client retries
Workflow deposits another Rs. 500
```

With the required header:

```http
Idempotency-Key: transfer-2026-07-30-001
```

Workflow stores that key with the customer and workflow type.

- Same completed request/key: return the original successful result; do not move money again.
- Same key while still in progress, failed, or compensated: return `409 Conflict`.
- Same key while compensation is waiting for an unavailable service: return `503 Service Unavailable`.
- New business attempt: use a new key.

This is why the key should be generated by the frontend/client once per user action and retained if it needs to retry.

## The Saga record

Workflow Service has its own persisted table:

```text
BANKING_WORKFLOWS
```

Its JPA entity is `WorkflowSaga` in `banking-workflow-service/src/main/java/com/oracle/banking/workflow/entity/WorkflowSaga.java`.

A row stores:

- Customer username
- Idempotency key
- Workflow type: `DEPOSIT`, `WITHDRAWAL`, `TRANSFER`, `ACCOUNT_OPENING`, or `BILL_PAYMENT`
- Workflow reference, such as `TRF-...`
- Source/destination account details
- Amount and description
- Account movement references
- Transaction references and IDs
- Current Saga status
- Failure/compensation information
- Created/updated timestamps

Even though Workflow currently uses the same Oracle database instance and `appuser` credentials as the other services, it owns this table logically. The other services should not update it.

## Account movements

Account Service records every workflow-driven balance change in:

```text
ACCOUNT_MOVEMENTS
```

For example, a transfer may create:

```text
TRF-abc:SOURCE:DEBIT
TRF-abc:DESTINATION:CREDIT
```

Each movement has a unique account/reference combination, operation, amount, and reversal state.

This gives Account Service two important guarantees:

1. Repeating the same movement reference does not change the balance twice.
2. A reversal can safely be requested repeatedly; only the first reversal changes the balance.

Account rows are pessimistically locked during balance changes, so two concurrent operations cannot both read the same balance and incorrectly spend it.

## Deposit flow

For a deposit, Workflow does this:

```text
Client -> Workflow: Deposit + Idempotency-Key
Workflow -> Workflow: Create and persist Saga
Workflow -> Account: Validate account ownership/status
Workflow -> Workflow: Persist planned credit reference
Workflow -> Account: Credit balance
Workflow -> Workflow: Persist completed account step
Workflow -> Workflow: Persist planned transaction reference
Workflow -> Transaction: Record credit transaction
Workflow -> Workflow: Mark Saga COMPLETED
Workflow -> Client: 200 success
```

The “persist planned reference before calling” detail is important.

Imagine Account Service applies the credit, but the network connection drops before Workflow receives the response. Workflow cannot know whether the credit happened. Because the planned reference was already stored, it can safely issue a compensating reverse command. That reverse command is idempotent: it is safe whether the original command succeeded or not.

## Withdrawal flow

Withdrawal is identical in shape, except Account Service debits first:

```text
Validate account
-> persist planned debit
-> debit account
-> persist planned transaction
-> record debit transaction
-> mark COMPLETED
```

Account Service rejects an insufficient balance. Since no money movement occurs in that case, Workflow marks the Saga as failed and returns the validation error—there is nothing to roll back.

## Transfer flow

Transfer is the more complex Saga:

```text
Client -> Workflow: Transfer + Idempotency-Key
Workflow -> Workflow: Persist STARTED Saga
Workflow -> Account: Validate source account
Workflow -> Account: Validate destination account number
Workflow -> Beneficiary: Verify beneficiary
Workflow -> Account: Debit source
Workflow -> Account: Credit destination
Workflow -> Transaction: Record source debit transaction
Workflow -> Transaction: Record destination credit transaction
Workflow -> Workflow: Mark COMPLETED
Workflow -> Client: 200 success
```

Before the debit, Workflow confirms:

- The source account exists.
- The caller owns the source account, unless they are an admin.
- Both accounts are active.
- The source has enough available balance.
- Source and destination are different accounts.
- The destination account belongs to a verified beneficiary for that customer.

Then it performs the money movement in the correct business order:

```text
1. Debit source account
2. Credit destination account
3. Record source debit transaction
4. Record destination credit transaction
```

## Bill-payment flow

Bill payment uses the same persisted Saga and reference-based compensation model:

```text
Client -> Gateway -> Workflow
Workflow -> Account: validate owner, status, and balance
Workflow -> Bill Payment: validate registered biller
Workflow -> Bill Payment: create PENDING payment by workflow reference
Workflow -> Account: debit by stable movement reference
Workflow -> Transaction: record BILL_PAYMENT debit transaction
Workflow -> Bill Payment: mark SUCCESS
Workflow -> Client: 201 success
```

If the workflow loses the response from pending-payment creation, compensation can find and cancel the payment using the workflow reference. If a later step fails, Workflow reverses the recorded transaction, reverses the debit, and cancels the bill payment in that order.

## Rollback / compensation

A distributed Saga does not have one database transaction across all services. That would be impractical in a microservice system.

Instead, every successful forward step has a compensating step.

For a transfer:

| Forward step | Compensation |
| --- | --- |
| Debit source account | Credit source account back |
| Credit destination account | Debit destination account back |
| Record source transaction | Mark transaction `REVERSED` |
| Record destination transaction | Mark transaction `REVERSED` |

Compensation is performed in reverse order:

```text
Reverse destination transaction
-> reverse source transaction
-> reverse destination credit
-> reverse source debit
```

For example, if source debit and destination credit succeed but Transaction Service is unavailable:

```text
Source balance:      Rs. 800 -> Rs. 750
Destination balance: Rs. 800 -> Rs. 850
Transaction recording fails
```

Workflow compensates:

```text
Destination: Rs. 850 -> Rs. 800
Source:      Rs. 750 -> Rs. 800
```

The request returns an error because the requested transfer was not completed. No half-transfer should remain.

## Saga statuses

| Status | Meaning |
| --- | --- |
| `STARTED` | Saga row created; validation/work has begun. |
| `SOURCE_MOVED` | Source debit or single-account movement completed. |
| `DESTINATION_MOVED` | Transfer destination credit completed. |
| `TRANSACTIONS_RECORDED` | Required transaction entries were recorded. |
| `COMPLETED` | Entire operation succeeded. |
| `COMPENSATING` | A failure occurred after a planned/applied step; rollback is running. |
| `COMPENSATED` | Rollback completed; balances/records are restored or reversed. |
| `COMPENSATION_PENDING` | A compensating participant was unavailable; retry is required. |
| `FAILED` | Failure occurred before any money movement was planned/applied. |

## What happens when rollback itself fails

Suppose Transaction Service is down when the workflow fails:

1. Workflow detects the original failure.
2. It attempts all compensations it can.
3. Account compensation may restore balances immediately.
4. Transaction reversal may fail because Transaction Service is offline.
5. Workflow stores `COMPENSATION_PENDING`.
6. The client receives `503 Service Unavailable`.
7. Workflow’s scheduler retries pending compensations every 30 seconds.

That scheduler is enabled in `BankingWorkflowServiceApplication`.

Once the unavailable service comes back, the retry completes and the Saga becomes `COMPENSATED`.

This avoids silently abandoning an incomplete rollback.

## Status-code behavior

| Situation | Response |
| --- | ---: |
| Successful workflow | `200 OK` |
| Missing `Idempotency-Key` | `400 Bad Request` |
| Invalid request, inactive account, insufficient balance, unverified beneficiary | `400 Bad Request` |
| Attempting another user’s account | `403 Forbidden` |
| Same idempotency key for a non-completed Saga | `409 Conflict` |
| Compensation still waiting for a service | `503 Service Unavailable` |
| A downstream service fails during the original workflow, but compensation succeeds | `502 Bad Gateway` |

A `502` means the requested operation did not complete because a participating service failed, but Workflow successfully restored consistency.

## Internal security

Workflow never calls public routes on downstream services. It calls `/internal/**` endpoints and supplies:

```http
X-Internal-Api-Key: <INTERNAL_API_KEY>
```

This prevents a browser/client from directly crediting accounts, recording transactions, or reversing movements.

The normal JWT proves who the user is to Workflow. The internal API key proves that Workflow is an authorised service caller to Account, Beneficiary, and Transaction services.

## Container connection setup

Workflow has its own configuration keys:

```env
WORKFLOW_DB_URL=jdbc:oracle:thin:@localhost:1521/FREEPDB1
WORKFLOW_DB_USERNAME=appuser
WORKFLOW_DB_PASSWORD=appassword
```

When running in Podman, Compose overrides only the URL:

```yaml
WORKFLOW_DB_URL: jdbc:oracle:thin:@host.containers.internal:1521/FREEPDB1
```

That is necessary because `localhost` inside a container is that container itself. The username and password come directly from `.env`.

## How to add a future Saga route

For example, imagine a “close account and transfer remaining balance” workflow.

The scalable pattern is:

1. Add a value to `WorkflowType`.
2. Add the public route/controller method.
3. Define the ordered forward steps in `BankingWorkflowService`.
4. Persist a planned reference before every remote command.
5. Persist progress immediately after every successful remote command.
6. Add the matching compensation in reverse order.
7. Reuse the existing `WorkflowSaga` table fields where possible; add a field only when the new workflow must remember something specific.
8. Require `Idempotency-Key`.
9. Test success, retry with the same key, each downstream failure point, rollback participant unavailability, and scheduled recovery after it returns.

That keeps future complex operations consistent without making all ordinary routes go through the orchestrator.

## What the orchestrator should not do

Do not send every request through it.

Good orchestrator candidates:

- Transfers
- Multi-account balance moves
- Loan disbursement involving account credit, loan record, and transaction record
- Card payment settlement
- Account closure with a final transfer
- Bill payment with balance debit, payment record, and external-provider interaction

Poor candidates:

- Account lookup
- List beneficiaries
- Mini statement
- Search transactions
- Update customer profile
- Simple single-service CRUD

Those should continue to go Gateway -> owning service directly.

## Kafka’s role

Kafka is not part of the correctness path for money movement right now.

Workflow completes the Saga and balance/transaction consistency first. Afterwards it emits events such as account-credited, account-debited, and transaction-created for future consumers such as notifications, audit, analytics, or fraud checks.

Inside Compose, Kafka is connected through the internal listener at `kafka:29092`; host-side tools use `localhost:9092`. After a successful banking workflow, Workflow Service resolves the customer's notification recipient through Auth Service's internal API and publishes an enriched `transaction-created` event. Notification Service consumes that event asynchronously, renders the selected template, sends the email over SMTP, and persists its delivery status. Notification delivery remains outside the Saga correctness path: an email failure must never roll back a completed banking operation.
